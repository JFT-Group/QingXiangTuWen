# 轻享图文 · 扩展脑暴

> 目的：原策划是一份“内容审核后台”的说明，不是完整的 UGC 社区。本文档列出它的结构性缺口、可加的创新能力、以及三档可落地的范围。所有结论待项目负责人拍板后回填《产品需求与业务说明书》与《开发规范》。
>
> **2026-11-18 已拍板**：M1 = 核心 CMS + 社交闭环（登录注册/BCrypt、图文 CRUD、先审后发、分类树、搜索、减少推荐、点赞/收藏、评论/回复、关注/粉丝、站内通知、审核者用户 CRUD、操作日志）；推荐算法、深色主题、话题/标签、风险分级、创作者等级后置到 M2/M3。本文档保留为 M2/M3 的脑暴底稿。

---

## 1. 原方案的 8 个结构性缺口

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 角色硬隔离：读者不能发布，创作者要单独身份 | 供给侧起不来；UGC 的核心是“任何人低门槛创作” |
| 2 | 全量“先审后发”，纯人工 | 审核成为吞吐瓶颈；没有机审、风险分级、信用体系 |
| 3 | 只有多级分类树，且号称无限层级 | 内容发现效率低；运营无法维护无限层级 |
| 4 | 没有推荐，首页只能按时间/分类 | 新内容无曝光，老内容沉淀，留存差 |
| 5 | 互动只有点赞/收藏 | 缺评论、关注、动态流，社区关系链建不起来 |
| 6 | 没有创作者成长体系 | 无等级、权益、激励、违规扣分，优质作者留不住 |
| 7 | 没有数据闭环 | 无埋点、曝光/点击/完读、实验，推荐和运营都靠拍脑袋 |
| 8 | 治理不完整 | 无举报、申诉、信用分、机审，只有“封号”一把锤子 |

## 2. 产品北极星

把原方案的“审核可控”升级为三角：

```text
可信内容  ←→  个性化发现  ←→  创作者成长
   │               │               │
审核/信用/举报   推荐/搜索/话题    等级/权益/数据
```

- **可信**是底线，不是卖点；用户默认内容已经过治理。
- **发现**决定留存：同一批内容，推荐做得好，次留和时长完全不同。
- **成长**决定供给：创作者要看到反馈、权益和上升通道。

## 4. 推荐系统：三阶段，不要一步到位

### v0 规则排序（约 1 周）

- **召回池**：最新、热门（时间衰减）、分类兴趣、关注作者、编辑精选。
- **排序分**（示例，权重可调）：

```text
score = w1*log(1+like) + w2*log(1+favorite) + w3*recency
      + w4*quality + w5*affinity
      - w6*seen - w7*report - w8*authorPenalty
```

- **多样性**：同作者每页最多 1 条；同分类最多 3 条；已读降权；新内容给探索位。
- **冷启动**：注册时选 3–5 个兴趣分类；新内容前 24 小时给固定探索流量。
- **负反馈**：不感兴趣、屏蔽作者、减少此类内容。
- **可解释**：卡片上可显示“因为你喜欢美食”“你关注的作者”。

> 这一档不依赖算法团队，纯后端 + 定时任务即可，先让“个性化”跑起来。

### v1 协同过滤（约 2–3 周）

- **item-based CF**：用户-内容互动矩阵，余弦相似度；离线定时计算，结果存推荐表。
- **召回**：CF + 热门 + 分类 + 关注 + 新鲜内容。
- **排序**：规则分 + CF 分加权；保留多样性与负反馈。
- **评估**：离线 precision@10、覆盖率、多样性；线上看 CTR、完读率、次日留存。
- **注意**：冷启动用户、长尾内容仍需规则兜底，不能全交给 CF。

### v2 向量召回 + 排序模型（4 周+）

- 内容向量：标题/正文/标签 embedding；用户向量：互动内容加权平均。
- 向量库：pgvector / Milvus / Redis Search 三选一，按团队熟悉度。
- 排序：LR/GBDT/LambdaMART，特征含用户、内容、上下文、交叉特征。
- A/B 实验框架：分桶、指标、显著性；先做“推荐 vs 时间序”对照。
- 这一档是路线图，不建议作为一期交付；除非团队有推荐经验。

**建议**：一期做 v0，二期做 v1；v2 写进路线图，不承诺时间。

## 5. 审核体系：从“全量人审”到“风险分级”

原方案的“全量先审后发”在内容量上来后必然堵死。建议：

1. **机审前置**：敏感词 Trie、正则（联系方式/外链）、图片鉴黄/暴恐/OCR（云 API）。
2. **信用分**：初始 100；违规扣分；高分创作者走“先发后审 + 抽查”，低分/新用户走“先审后发”。
3. **风险分级**：新账号、低信用、敏感分类、含外链、多图 → 高风险；高信用、低风险 → 快速通道。
4. **人工工作台**：风险提示、相似内容聚合、快捷键、批量通过/驳回、常用理由。
5. **申诉**：作者对驳回/下架/封禁可申诉；复核记录留痕；误杀可恢复。
6. **指标**：审核时效、误杀率、漏放率、申诉率、机审拦截率。

> 如果一期坚持“全量先审后发”，也可以，但要在文档里承认这是“演示/课程场景”的取舍，不要写成“企业级最佳实践”。

## 6. 内容组织：分类 + 标签 + 话题

- **分类**：稳定骨架，运营强控，建议最多 3 级；用于导航与权限/运营分区。
- **标签**：创作者自选 + 运营推荐，扁平结构；用于检索、推荐、相似内容。
- **话题**：运营发起，带时间窗口；聚合内容、可上热门榜；是站内流量的主要抓手。
- **合集/专栏**：作者自建系列，支持连载；提升关注与完读。
- **搜索**：标题/正文/作者/标签；MySQL 8 `ngram` 全文索引可先顶上，量级上来再换 Elasticsearch；加热搜词与搜索联想。

原方案的“无限层级分类”建议改成“系统支持多级，运营规范最多 3 级”，否则运营会疯。

## 7. 社交与增长

- **评论/回复**：支持一级评论 + 回复；评论也要机审 + 举报 + 管理员删除。
- **关注/粉丝**：作者主页、关注流、粉丝数；关注流与推荐流并列。
- **通知**：审核结果、评论、点赞、关注、系统公告；一期可轮询，二期 SSE。
- **分享**：详情页链接、分享海报（二维码 + 作者 + 标题）。
- **榜单**：日/周热门、新锐作者；榜单要防刷，权重含质量分。
- **创作者等级**：新手 / 活跃 / 优质 / 认证；权益：优先审核、曝光加权、数据面板、认证标识。
- **激励**：流量扶持、活动、badge；不做现金和积分商城，避免复杂运营。

## 8. 技术增强（与产品能力对应）

| 能力 | 轻量方案 | 进阶方案 | 何时升级 |
|---|---|---|---|
| 推荐 | SQL + 定时任务 + Redis 缓存 | 离线特征 + 在线排序 / 向量召回 | 日活/内容量上来后 |
| 搜索 | MySQL FULLTEXT + ngram | Elasticsearch | 搜索 QPS 或召回要求提高 |
| 机审 | 本地敏感词 + 正则 | 云内容安全 API（文本/图片） | 有真实违规压力 |
| 异步 | Spring `@Async` + 线程池 | Outbox 表 + MQ | 通知/特征更新要求可靠 |
| 缓存 | Caffeine 本地缓存 | Redis（热榜、feed、限流、令牌黑名单） | 多实例或热点明显 |
| 通知 | 轮询 | SSE / WebSocket | 实时性要求提高 |
| 埋点 | 事件表 + 每日聚合 | 埋点 SDK + 数仓 | 需要实验与精细化运营 |
| 实验 | 配置开关 + 用户分桶 | 实验平台 | 多实验并行 |
| 存储 | 本地磁盘 + 接口抽象 | MinIO / 云 OSS | 多实例或容量压力 |
| 可观测 | 日志 + actuator | Prometheus + Grafana | 上线后排障需要 |

## 9. 三档范围建议

### 档 A：稳（3–4 周）

UGC 核心闭环 + 推荐 v0 + 评论 + 分类/标签 + 敏感词机审 + 基础埋点。

适合：课程答辩、时间紧、要保证演示稳定。

### 档 B：均衡（6–8 周，推荐）

档 A + 关注/动态流 + 话题 + 风险分级 + 云机审 + 创作者等级 + 全文搜索 + 通知中心 + 举报/申诉（简化）。

适合：想做出“市面上常见 UGC 产品”的完整感，又不想被算法拖死。

### 档 C：激进（10–12 周）

档 B + 协同过滤推荐 + 信用分 + A/B 实验 + 榜单 + 分享海报 + 合集/专栏 + 防刷风控。

适合：团队有推荐/后端经验，目标是比赛或真实上线。
